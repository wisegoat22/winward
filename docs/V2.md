# Winward v2: decisions that survive an observed result

The v2 lab is at **http://127.0.0.1:8765/v2**. The original v1 policy remains at `/policy` with unchanged weights.

Three components now make different claims:

1. **Learned policy:** ranks structured candidate actions from random-initialized weights. It does not read Python or write a patch.
2. **Uncertainty reference:** searches possible worlds and observation branches up to five actions deep. It can choose inspection, clarification, a repair, or finishing. This is an algorithm, not an acquired neural-model capability.
3. **Coding harness:** creates trusted Python fixtures in temporary directories, exposes two supplied patch candidates after inspection, runs actual subprocess acceptance checks, and feeds observed results back into the next decision. A failed check overrides an optimistic forecast. A changed goal invalidates an old passing result.

The working rule is **choose one action, observe, reconsider**. Each decision has at most five actions of lookahead; a coding episode may take up to 16 actions. Finishing requires a real passing check for the current source and goal. Permissions, candidate availability, and finish checks are enforced code, not evidence of learned judgment.

## What the experiments found

The first v2 checkpoint trained on 64,000 synthetic goal-changing graphs. It improved goal selection but lost completion performance. The matched fresh-instance audit reported:

| Same cases, seed 110000000 | V1 | V2 |
| --- | ---: | ---: |
| Paired-goal next actions | 88.75% | 97.25% |
| Both choices correct within a goal pair | 155/200 | 189/200 |
| Mixed graph tasks completed | 267/300 | 255/300 |
| Fresh legacy tasks completed | 292/300 | 240/300 |

On 40 actual coding fixtures across five generated families, v2 verified only **4/40**, deferring on the other 36; evidence-first rules verified **40/40**. The neural model made no edits. These results are preserved in [the original v2 reports](../reports/v2/). They motivated new training data; those test instances were not reused as training examples.

### Separate v2.1 tools candidate

The follow-on candidate again starts from random weights: **4,759,809 parameters**, with no pretrained, v1, or v2 weights loaded. Its 64,000 rows combine:

- 32,000 synthetic goal/cost examples.
- 32,000 fact/action permutations of **1,218 actual observed decisions** from 128 boundary/rounding training episodes. These are augmented observations, not 32,000 independent coding tasks.

The teacher for observed tool decisions is a simple evidence-first rule using public observed state: clarify missing requirements, check, inspect after failure, try an untested supplied patch, check again, finish when verified. Equally priced and structurally indistinguishable unverified patches share target probability. The teacher never consults hidden patch correctness to select the action. Source text is shown to humans but ignored by the numeric policy.

Separate validation includes 32 collected episodes, 2,400 observation permutations, and 16 further real rollouts. Validation selected **step 1,500 of 6,000**. Only then were test instances generated; the checkpoint stayed frozen afterward.

| Same fresh cases, graph seed 240000000 | V1 | V2.1 tools |
| --- | ---: | ---: |
| Paired-goal next actions | 88% | 96.25% |
| Both choices correct within a goal pair | 153/200 | 185/200 |
| Overall next-action agreement | 87.54% | 92.08% |
| Mixed graph tasks completed | 263/300 | 248/300 |
| Fresh legacy tasks completed | 295/300 | 239/300 |
| Previously inspected 20-pair goal diagnostic | 52.5% | 90% |
| Previously inspected downstream-cost diagnostic | 100% | 82.5% |

This is a specialized candidate, **not an across-the-board improvement**. V1 is retained. Reusable diagnostics are not a blind benchmark, and the two tables use different fresh datasets, so compare each candidate with its matched v1 baseline.

### Actual coding tasks

The final tools audit reserved the **interval** code family and seed **230000000** from model training and validation. It uses inclusive versus exclusive range requirements, two supplied patches, and real check execution. Forty instances combine known/unclear requirements and stable/revised goals.

| Same 40 interval tasks | Verified and finished | Mean actions | Mean total time |
| --- | ---: | ---: | ---: |
| V2.1 tools candidate | 40/40 | 9.6 | 128.83 ms |
| Evidence-first rules | 40/40 | 9.6 | 96.64 ms |
| Random eligible action, including defer | 2/40 | 3.18 | 11.37 ms |

The model matched the simple rules' completion and action counts but was slower. Random's low cost mostly reflects giving up. Costs must always be read alongside success. The model generated zero language tokens; tool-token costs remain declared estimates. Wall time, decision time, subprocess time, and read/write/output byte counts are measured. These are single-session observations on a shared Mac, not an isolated throughput benchmark. One-time checkpoint initialization is reported separately.

This family was excluded from optimization, but developers inspected its template and tested the harness. Its numeric tool-state protocol is shared with training families. **40/40 does not establish reliability on real repositories, code generation, or arbitrary instructions.** The earlier v2 coding audit used different task families; it is not a matched 4-to-40 comparison.

## How uncertainty is handled

The separate belief planner takes explicit possible worlds, probabilities, permitted actions, effects, and observation labels. An action's observation updates the belief; the next action can differ across branches. It maximizes modeled verified completion probability, then minimizes expected weighted token/time cost, then expected steps. It cannot see an actual hidden world.

The planner prunes actions with no effect or information gain, memoizes repeated beliefs, stops at verified goals, and avoids further expansion when the only effective action finishes immediately. It has a node budget and reports incomplete search explicitly. It is not a general learned value-of-information system. Its probabilities and effects are supplied assumptions, and a bounded-search failure does not prove impossibility.

Built-in demonstrations cover inspect-versus-act, missing requirements, revised goals, and uncertain action outcomes. Their modeled success values are constructed examples, not evaluation win rates.

## Reproduce on Mac

Install dependencies with `uv sync --frozen`. First train v1 as described in the root README so matched audits have their baseline checkpoint. Existing run directories are protected from overwrite.

```sh
# Optional: reproduce the first v2 experiment and its preserved failure record.
.venv/bin/python -m agent_training.train_v2
.venv/bin/python -m agent_training.evaluate_v2 --run runs/goalpolicy-v2
.venv/bin/python -m agent_lab.benchmark --run runs/goalpolicy-v2 \
  --kinds boundary rounding collection already_correct timeout

# Train the separate tools candidate from scratch, collecting actual outcomes.
.venv/bin/python -m agent_training.train_tools

# Freeze first; then evaluate on the predeclared test seeds and task family.
.venv/bin/python -m agent_training.evaluate_v2 \
  --run runs/goalpolicy-v2-tools --fresh-seed 240000000
.venv/bin/python -m agent_lab.benchmark \
  --run runs/goalpolicy-v2-tools --seed 230000000 \
  --kinds interval --seeds-per-condition 10

.venv/bin/python scripts/server.py start
```

Open `/v2` for the tools candidate. The default v2 runtime is pinned to `runs/goalpolicy-v2-tools`; audits are shown only if their checkpoint hash matches. Weights, optimizer runs, and datasets are local artifacts excluded from Git. Public reports preserve results without user paths or credentials. Reproducing these published tests is not a new independent audit.

## Execution boundary and next research work

The coding harness writes fixed filenames inside disposable directories and executes only trusted generated Python with a fixed command, minimal environment, and timeout. The local API accepts only task kind, seed, policy, and two Boolean scenario controls; it cannot accept code, commands, or a filesystem path. It is **not an operating-system security sandbox** and must not be used to execute arbitrary code. No real user repository is edited.

Broader completion and cost sensitivity still need work. The next model should learn from diverse observed failures without losing existing planning behavior, and must beat appropriate simple baselines on success and total cost. More parameters alone do not solve this gap; the present evidence does not justify calling this a general 4B agent model.
